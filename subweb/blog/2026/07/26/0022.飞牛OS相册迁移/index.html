一、背景

飞牛OS是目前无需”黑“就能实现多种专业功能，好用且免费的Nas系统，但是如果需要迁移Nas，从一台换到另一台，飞牛官方暂未给出合适的解决方案。尤其是对于相册等应用的数据，相册中的AI识别数据、图像位置数据、相册分类数据等十分珍贵，迁移后需要重新构建并不方便，在此背景下，本文提出了一种近乎无损的方法，直接修改和迁移数据库文件，让迁移数据不再麻烦。

本流程可用性已由本人亲自测试，下面步骤为本人迁移时完成，迁移目标机器的fnOS版本为1.2.0203，相册版本为0.9.7，本文只确定在此版本下能正常工作，修改系统文件有风险，请确保自己有承担风险的能力和基本计算机知识，最好有Linux方面知识。请提前备份数据，如出现数据丢失等问题，本人概不负责。

二、准备工作

1. SSH连接正常

由于本文的方法需要处理系统级文件，在图形界面无法查看，因此需要使用ssh连接到Nas，请确保ssh为打开状态，并保证能连接，本文使用Xshell作为连接ssh的连接工具，也可以选择其它工具甚至直接使用windows子带的ssh，选择Xftp作为文件传输方式，没有该文件传输方式也可以将需要修改备份的文件放到存储空间内下载。下面为ssh连接的步骤。

2. 停用相册或卸载相册

原Nas中将相册停用，新Nas若安装也要停用，最好是卸载，本文中新的Nas还未安装相册，因此仅需要将原Nas中的相册停用即可。可在应用中心 - 已安装 - 相册中选择停用。如果你要卸载，请选择保留数据卸载。

停用或卸载相册后，才能确保数据库不会再被读取，新Nas安装后，相册会以为以前安装过，数据还留在Nas上。

3. 安装可以读取SQLite的工具

可以安装Navicat或SQLiteStudio作为读取sqlite文件的工具。由于Navicat收费，本文选择了SQLiteStudio。安装方法非常简单，也可参考其它文档，本文不再赘述。

附录A：AI生成的数据库解释

本附录根据飞牛相册 SQLite 数据库导出的 SQL 结构整理，主要用于数据研究、备份恢复和二次开发参考。

字段含义由 SQL 注释、字段命名、索引及表间关系综合推断，并非飞牛官方数据库文档。对于 SQL 中没有给出枚举或单位的字段，本文会明确标注“具体含义未声明”。

1. 阅读说明

1.1 时间字段

数据库中大量使用 INTEGER 保存时间，例如：

  • created_at
  • updated_at
  • mod_time
  • delete_at
  • last_heartbeat

它们通常是 Unix 时间戳，但 SQL 结构没有统一说明使用秒、毫秒还是其他精度。实际处理前，建议先抽取几条数据进行验证。

1.2 表之间的关联

SQL 导出文件中执行了：

而且多数业务表并没有显式声明外键。因此，本文所写的关联关系主要根据字段名和索引推断。

1.3 布尔与枚举字段

以下类型字段通常使用整数表示状态：

  • status
  • source
  • shared
  • deleted
  • is_live
  • is_collect
  • special_type

除 SQL 中已有注释的字段外，具体枚举值不能仅凭数据库结构确定。

1.4 空间扩展表

数据库包含大量 SpatiaLite 表和虚拟表，例如：

  • geometry_columns
  • spatial_ref_sys
  • idx_photo_geom
  • SpatialIndex
  • KNN

这些对象主要用于照片 GPS 坐标、地图查询和空间索引，一般不建议手动修改。

2. 核心数据关系

核心结构可以简单理解为：

  • photo 保存磁盘上的实际媒体文件信息。
  • user_photo 保存媒体文件在某个用户相册空间中的实例。
  • user_album 保存相册。
  • album_user_photo 连接相册和用户照片。
  • face 保存照片中检测到的人脸。
  • person 将多个人脸聚合为同一个人物。
  • user_tag 和 user_photo_tag 负责标签系统。

3. 核心业务表

用户与 NAS 用户账户的映射表。

6. 修改数据库时的注意事项

  1. 修改数据库前，应停止飞牛相册相关服务，并备份原数据库文件。
  2. 不建议直接修改 geometry_columns、spatial_ref_sys、idx_photo_geom* 等空间扩展内部表。
  3. photo 是底层文件资源，user_photo 是用户照片实例，删除时必须同时检查两个层级。
  4. 删除 user_photo 前，还应检查以下关联表：
    • album_user_photo
    • user_photo_tag
    • user_photo_category
    • face
    • repeat_photo
    • recycle_bin
  5. 修改 photo.file_path 后，应用层缓存、缩略图路径或文件索引不一定会自动同步。
  6. 修改 GPS 坐标时，除了 latitude 和 longitude，还可能需要同步更新 geom 及其 R-Tree 空间索引。
  7. 数据库没有完整使用外键约束，手动删除记录不会自动清理所有关联数据。
  8. status、source、category 等枚举字段应先观察现有数据取值，再进行修改。
  9. file_hash 和 original_hash 可能参与文件校验或重复照片识别，不应随意修改。
  10. recover_info 很可能保存序列化恢复信息，编辑后可能导致回收站记录无法恢复。
